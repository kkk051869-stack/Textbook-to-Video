# JSON → HTML 生成链路修复计划

| 项 | 内容 |
|----|------|
| 文档状态 | 实施中（P0 已落地，见 §9） |
| 创建日期 | 2026-06-03 |
| 范围 | `src/textbook2video/animation_gen.py` 为核心的 storyboard JSON → 单文件 HTML 链路 |
| 核心结论 | 病根是**复杂度过载**，修复方向是**减复杂度 / 复用已有能力 / 往规则挪**，而非新增容错机制 |

---

## 0. 一句话本质

> 上游系统性地放大输出复杂度 → 中间用最脆弱、零容错的解析器（正则手写栈）接收 → 而下游真正的消费者（浏览器）其实根本不在乎这些错误。

报告的 5 个现象问题都是这条链上的症状，不是 5 个独立 bug。

---

## 1. 问题清单（现象）

| # | 现象 | 位置 |
|---|------|------|
| P1 | LLM 输出 `<div>` 开闭不平衡（如 25 open / 21 close），栈匹配 depth 永远到不了 0，提取返回空 | `_extract_slide_divs` |
| P2 | LLM 不按要求输出正确数量的 slide（期望 2 实际 1） | `generate` 数量校验 |
| P3 | Prompt 复杂度相比早期版本大幅膨胀（动画子系统从 1 个涨到 7 个） | `slide_content_core.md` |
| P4 | 提取逻辑零容错，只有 `depth == 0` 才提取，无 fallback | `_extract_slide_divs` |
| P5 | `extract_slides` 兜底返回原始文本，对下游无修复作用（假兜底） | `extract_slides` |

---

## 2. 根因分析（三层）

### 第一层：结构性根因（问题来源）

**根因 1 — 同一份 HTML 存在两套宽容度不同的解析器**

| 环节 | 解析方式 | 对 div 不平衡 |
|---|---|---|
| 提取（Python） | `_extract_slide_divs` 正则 + 手写栈 | **致命**，返回空 |
| 布局 QA（`check_layout.py`） | 浏览器 DOM | 免疫 |
| CSS 热修复（`css_hotfix.py:255` `page.content()`） | 浏览器 DOM | 免疫，且会把补齐后的 HTML 写回磁盘 |
| 播放（`slide-controller.js:41` `querySelectorAll('.slide')`） | 浏览器 DOM | 免疫 |

→ 不平衡的 HTML 如果能进浏览器，渲染/录制/播放全部正常。唯一判它"死刑"的是提取这一步，而它用的是整条链上最脆弱的技术，还放在最前面当守门员。**P1/P4/P5 的本质是"用错了解析器"，不是"缺一个 fallback"。**

**根因 2 — 上游 storyboard 被设计成"主动制造复杂度"**

- `storyboard.md:134`：「每个 segment 的 elements 数组必须有 5-10 个元素…不要只给 2-3 个元素！」
- `storyboard.md:153`：「对比页：至少 7 个元素」
- element 类型本身深度嵌套：`comparison_panel`（`items:{title,content,icon}[]`）、`icon_group`、`flow_step`
- `check_layout.py:268`：`too_few_visible_elements` 为 **fail 级**，元素少了直接触发昂贵修复循环

→ 形成对抗回路：上游命令"多塞元素填满 1920×1080" → LLM 生成几十层嵌套 → 闭合标签越多越容易漏 → 提取器零容错崩掉。**P1 不是 LLM 偶然失误，是被系统设计逼出来的。**

### 第二层：设计性根因（放大器）

**根因 3 — Prompt 已顶到硬天花板，用"卡上限"代替"减负担"**

- `slide_content_core.md` 模板正文 = **4467 字符**
- 回归测试 `test_animation_prompts.py:37` 断言 `len(template) <= 4500`
- **只剩 33 字符余量**
- 一个 prompt 塞了 7 个正交动画子系统：`.anim` 15+ 类、`data-step`、`data-anim-id`、`svg-draw`、FLIP、`deco-follow`、6 个持续微动类

→ 团队已意识到膨胀（加了上限测试），但应对是"守住上限"而非"减少认知负担"。指令数量与遵从率成反比，是 P1/P2 的共同温床。

**根因 4 — 模型能力约束被整个方案忽视**

- 底层模型：`ecnu-max`=DeepSeek-V4-Flash / `ecnu-plus`=Qwen3.6-27B（`config.py:67`）
- 走华东师大 OpenAI-compatible 网关，`client.py:25` 强制 `openai/` 前缀
- 后果一：这类开源模型在"长指令遵从 + 深嵌套标签闭合"上明显弱于 Claude/GPT，同一 prompt 一次过率更低——P1/P2 有一部分是模型能力天花板，prompt 补不动
- 后果二：第三方 OpenAI-compatible 网关对 `response_format: json_schema` / tool calling 的支持常常残缺或不稳定，**"结构化输出"方案在此不可靠**
- 附带：`animation_gen.py:38` `TEMPERATURE = 0.7`，对"结构必须精确"的任务偏高

**根因 5 — 职责错配：让 LLM 干它最不擅长的活**

当前架构让 LLM 在一次生成里同时负责 6 个正交维度：

```
语义内容 + 视觉布局 + 动画类编排 + 延迟顺序 + 时间轴标记 + SVG描边/FLIP
   ↑                                                          
LLM 唯一真正擅长的     ←—— 其余 5 个都是确定性规则能生成的 ——→
```

→ 项目自己已证明规则能接管：`build_slide_timelines`（从 `trigger_at_sec` 算时间轴）、`infer_transitions`、`TRANSITION_RULES` 全是 Python 确定性生成。**团队知道这条路但没贯彻**——动画类、延迟、`data-step` 仍压给 LLM 手写。LLM 最不可靠的能力（精确结构标记、深嵌套闭合）被委以重任。

### 第三层：实现性根因（为什么没被提前发现 / 修复无力）

**根因 6 — 错误处理哲学在同一条 pipeline 里自相矛盾**

| 位置 | 态度 | 问题 |
|---|---|---|
| `parse_storyboard` | 严格 fail-fast（数量不符直接 raise） | |
| `extract_slides` 兜底 | 静默返回原始文本 | 假兜底：把错误延迟到下游、爆在信息更少处 |
| `generate()` 末尾占位 slide | 降级容忍 | 真容忍，但提取已先崩，走不到这里 |

- P5 的兜底 `return text, custom_css` 只是把"立刻报错"换成"晚点报错"
- 修复预算吝啬：`MAX_BATCH_COUNT_REPAIR_ATTEMPTS = 1`，单 slide 修复也只一轮

**根因 7 — 测试覆盖盲区，最脆弱处在裸奔**

- `test_animation_prompts.py` 全是 prompt 字符串拼接断言
- 唯一的提取测试 `test_extract_slide_divs_ignores_commented_divs` 只测了"忽略注释 div"
- **零测试**覆盖：div 不平衡、数量不符、修复链实际行为、脏 LLM 输出
- 所有测试都不调真实 LLM——真实失败率从未进入 CI

→ 团队在"prompt 长度"上加了回归守卫，却在"提取鲁棒性"（最致命环节）上一个测试都没有。

---

## 3. 修复原则

1. **减复杂度优先**：能删的不加，能用规则的不交给 LLM。
2. **复用已有能力**：项目已集成 Playwright/浏览器（最强容错解析器），不引入新依赖（如 BeautifulSoup）。
3. **不加"会制造假象成功"的机制**：BS4 补错位置、占位 slide 掩盖失败，都会让根因 6 的"假容忍"恶化。
4. **真实脏数据驱动测试**：守护提取鲁棒性，而非只守 prompt 长度。

> 反模式警示：任何"加新容错机制"的方案（BS4、结构化输出、再加一层修复 LLM）都是在往复杂度过载的系统里加复杂度，会成为下一个根因 3。

---

## 4. 修复方案（分阶段）

### 优先级总览

| 编号 | 修复 | 治根因 | 是否减复杂度 | 风险 | 阶段 |
|------|------|--------|------|------|------|
| F1 | 提取改用浏览器 DOM 解析 | 1、4、6 | ✅ 删脆弱正则栈 | 低 | P0 |
| F2 | 砍 storyboard "5-10 元素"硬要求 + 精简 prompt 动画子系统 | 2、3、5 | ✅✅ 负复杂度 | 低-中 | P0 |
| F3 | 真兜底链 + 重试预算 1→3 | 6 | ➖ 不增不减 | 低 | P0 |
| F4 | 补提取/数量/脏数据测试 | 7 | ➖ 防恶化 | 低 | P0 |
| F5 | 动画类/延迟/data-step 改由 Python 注入 | 3、5 | ✅✅ prompt 砍 50%+ | 中 | P1 |
| ❌ | BS4 容错解析 | — | ❌ 加复杂度 | 掩盖根因 | 不做 |
| ❌ | tool_use / json_schema 结构化输出 | — | ❌ 网关不支持 | 不做 |

---

### P0 — 立即修复（低风险、高 ROI，1-2 天）

#### F1：提取改用浏览器 DOM 解析

- **目标**：让提取阶段与下游消费者（浏览器）用同一套容错解析器，消除"两套宽容度"错配。
- **治根因**：1、4、6。一举消解 P1/P4/P5。
- **改动位置**：`animation_gen.py` 的 `_extract_slide_divs` / `extract_slides`。
- **做法**：
  - 用项目已有的 Playwright，把 LLM 输出包成最小 HTML（`<body>{llm_output}</body>`）加载，`page.eval` 取 `document.querySelectorAll('.slide')` 的 `outerHTML` 列表。
  - 浏览器会自动把不平衡 div 补齐到 DOM 树语义位置，得到的 slide 与最终渲染一致。
  - 保留旧栈匹配作为**快路径**：先栈匹配，数量正确就直接用（避免每批都启浏览器的开销）；数量不足才走浏览器兜底。
- **不做**：不引入 BeautifulSoup（新依赖 + 会补到错误位置，制造静默劣化）。
- **风险**：低。浏览器与下游一致，不会"修出"下游看不到的结构。唯一成本是兜底路径需启动浏览器（仅失败批触发，可接受）。
- **验收**：
  - 给定 `25 open / 21 close` 的样本 HTML，提取出与浏览器渲染一致的 N 个 slide。
  - 快路径命中时不启动浏览器（性能回归测试）。
- **回滚**：F1 是函数内替换，保留旧实现为快路径，回滚只需移除兜底分支。

#### F2：砍上游复杂度要求 + 精简 prompt

- **目标**：从源头降低 LLM 的输出复杂度与认知负担。
- **治根因**：2、3、5。降低 P1/P2 发生概率。
- **改动位置**：`storyboard.md`、`slide_content_core.md`、`check_layout.py:268`、`test_animation_prompts.py:37`（上限断言相应下调）。
- **做法**：
  1. **storyboard 端**：把"必须 5-10 个元素""不要只给 2-3 个"改为**建议区间**（如 3-6），去掉感叹号式硬命令；`too_few_visible_elements` 从 `fail` 降为 `warn`。
  2. **prompt 端**：逐一审计 7 个动画子系统，列出"砍掉后最终视频实际看不出差异"的项先删（候选：`svg-draw`、FLIP、`deco-follow`、部分持续微动类）。每删一项，prompt 正文字符数下降，遵从率上升。
  3. 删后下调 `test_animation_prompts.py:37` 的上限断言到新值，**让测试守护"已瘦身"而非"接近爆表"**。
- **风险**：低-中。视觉可能朴素一点，需要人工看几个样片确认可接受。属可逆的 prompt 改动。
- **验收**：
  - 模板正文字符数显著下降（目标 < 3500）。
  - 抽样 N 个 storyboard 跑端到端，P1（div 不平衡）/P2（数量错）发生率下降。
  - 人工评审样片视觉质量无明显回退。
- **回滚**：prompt / storyboard 是纯文本，git revert 即可。

> F2 的前置动作：先做一次「动画子系统 → 是否在最终视频可见」的盘点表（见 §6 附录模板），用数据决定砍哪些，避免凭感觉删。

#### F3：真兜底链 + 重试预算

- **目标**：让 `extract_slides` 的兜底真正接到 `generate()` 已有的占位补齐逻辑，统一错误处理态度。
- **治根因**：6。让 P5 的假兜底变真。
- **改动位置**：`extract_slides`、`MAX_BATCH_COUNT_REPAIR_ATTEMPTS`。
- **做法**：
  - `extract_slides` 提取失败时，依次：① 快路径栈匹配 → ② F1 浏览器解析 → ③ 仍失败则返回明确的"空 + 失败标记"，让上层走数量修复 / 占位补齐，而不是返回易被误判为正文的原始文本。
  - `MAX_BATCH_COUNT_REPAIR_ATTEMPTS` 1 → 3（纯参数，止血）。
- **风险**：低。重试只增加耗时/调用数。
- **验收**：提取彻底失败时 pipeline 仍能产出占位 slide 走完，不抛未捕获异常。
- **回滚**：参数与分支可独立回退。

#### F4：补提取 / 数量 / 脏数据测试

- **目标**：守护最脆弱环节，让真实失败模式进入 CI。
- **治根因**：7。
- **改动位置**：`tests/`。
- **做法**：新增用例覆盖——
  - div 不平衡（多开 / 多闭）→ F1 提取仍得到正确 slide 数；
  - LLM 少输出 / 多输出 slide → 数量修复行为；
  - 含 `<style>`、markdown 包裹、`<!DOCTYPE>` 兜底的脏输入；
  - 提取彻底失败 → 占位补齐路径。
  - 用录制好的"脏 LLM 输出样本"做 fixture，不依赖真实网关。
- **风险**：极低。
- **验收**：上述用例全绿，并能复现报告中的 P1/P2 场景。

---

### P1 — 中期重构（治本，3-5 天）

#### F5：动画类 / 延迟 / data-step 改由 Python 注入

- **目标**：贯彻项目已有的 `build_slide_timelines` / `infer_transitions` 思路，把动画编排从 LLM 手里彻底收回。
- **治根因**：3、5。根治 P3，并大幅压低 P1/P2。
- **改动位置**：新增后处理模块（如 `animation_inject.py`）；`slide_content_core.md` 大幅瘦身；`build_scenes_description` 输出语义角色标记。
- **做法**：
  - LLM 只输出**极简语义 HTML**：`<div class="slide" data-visual="process"><h1 data-role="title">…</h1>…</div>`。
  - Python 后处理按 `data-role` + 出现顺序 + storyboard 的 `animations` 数组，确定性注入 `.anim`/`.anim-up`/`.dN`/`data-step`/`data-anim-id`。
  - prompt 删去全部动画系统说明（预计砍 50%+ 字符）。
- **风险**：中。一次性重构，短期视觉细节需重新用规则表达；建议在 F1-F4 稳定后单独分支推进。
- **验收**：
  - prompt 正文 < 2000 字符；
  - 动画行为可单元测试（给定语义 HTML + storyboard → 确定性输出带标记 HTML）；
  - 端到端 P1/P2 失败率较 P0 后再降一个量级。
- **回滚**：作为独立分支，未达标不合并。

---

### 明确不做

| 方案 | 不做的原因 |
|------|-----------|
| BeautifulSoup 容错解析 | 引入新依赖；会把缺失 div 补到错误位置 → 静默视觉劣化，比报错更难发现；与下游浏览器解析行为不一致 |
| tool_use / json_schema 结构化输出 | 底层是第三方 OpenAI-compatible 网关，对结构化输出支持不稳定；且让 LLM 在 JSON 里转义 HTML 比自由写更费劲，可能整体降低内容质量 |
| 再加一层"修 HTML 的 LLM" | 往复杂度过载系统加复杂度，成为下一个根因 3 |

---

## 5. 实施顺序与依赖

```
F1（提取改浏览器）──┐
F3（真兜底+重试）──┼─→ F4（补测试，锁定 P0 成果）──→ 观察一周失败率
F2（砍复杂度）─────┘                                      │
                                                          ↓
                                          失败率仍 > 阈值？──是──→ F5（动画注入重构）
                                                          │
                                                          否 → 停在 P0，不做 F5
```

- F1 / F2 / F3 相互独立，可并行。
- F4 依赖 F1（要测新提取路径）。
- **F5 是条件触发**：只有 P0 全部落地并观察后失败率仍不达标才启动，避免过早大重构。

## 6. 验收标准（总）

| 指标 | 当前（报告） | P0 目标 | P1 目标 |
|------|------|------|------|
| 提取失败率（div 不平衡导致空列表） | 偶发致命 | ≈ 0 | ≈ 0 |
| slide 数量一次正确率 | 偏低（batch=2 出现 1/2） | 明显提升 | 接近 100% |
| prompt 模板正文字符数 | 4467（顶上限） | < 3500 | < 2000 |
| 提取 / 数量 / 脏数据测试覆盖 | 1 个（仅注释） | 覆盖主要脏输入 | 含动画注入单测 |
| 端到端跑完率（不抛异常） | 提取崩则中断 | 始终走完（占位兜底） | 同 |

## 7. 风险与回滚

- 所有 P0 改动均为**函数内替换 / 纯文本 / 参数**，可独立 git revert，互不耦合。
- F2 唯一主观风险（视觉变朴素）由"人工评审样片"关卡兜住，不达标不合并。
- F5 走独立分支，作为条件项，天然隔离。
- 统一回滚顺序：F5 → F2 → F4 → F3 → F1（按耦合度逆序）。
